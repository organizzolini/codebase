# caelundas-api

Serves the astronomical events `caelundas-cli` writes to the Caelundas Postgres to `caelundas-web` over GraphQL, reading them through `CaelundasDatabaseModule` from `@codebase/caelundas-db`. It answers the `health` query, the calendar's events, tag facets, and dataset span, and `nightSky`, which draws the animated star-field backdrop. Runs locally on `CAELUNDAS_API_PORT`; `.env.default` sets 6173.

## Stack

- **GraphQL server**: Apollo Server via `@nestjs/apollo` (`ApolloDriver`).
- **Schema**: code-first, emitted to `src/schema.gql` beside the root module (`GRAPHQL_SCHEMA_FILE`), whatever the working directory; the file is gitignored.
- **Database**: Postgres through `CaelundasDatabaseModule` (`@codebase/caelundas-db`, which wraps the shared `DatabaseModule` from `@codebase/persistence`); no file is opened. Connects as `caelundas_username` to `caelundas_development`.`caelundas` with the `CAELUNDAS_POSTGRES_*` variables, which `environmentSchema` takes from `postgresEnvironmentSchema({ project: "caelundas" })`. Migrations run separately with `nx run caelundas-db:migration:run`.
- **CORS**: `CorsModule` (`modules/cors`) provides the options the bootstrap enables, from `CAELUNDAS_API_CORS_ORIGINS` (comma separated, default empty; `.env.default` lists the web app's dev origins). No origin is allowed until you list one, so a browser app on another origin is refused by default; `*` allows every origin and suits only a public API. The bootstrap calls `app.enableCors(app.get(CorsService).getOptions(...))`: the CORS middleware answers the browser's `OPTIONS` preflight before Apollo sees it, so Apollo's CSRF prevention, which would answer it with 400, never runs.

## Modules

- `cors/` — works out the CORS options the browser's preflight is answered with (`CorsService`).
- `events/` — reads the calendar's events, tag facets, and dataset span (`EventsService`).
- `health/` — the health check query every API here answers (`HealthService`).
- `night-sky/` — serves the night sky (`NightSkyService`). It holds the stars and constellation figures in memory, read once at startup from the rows `caelundas-cli night-sky` ingests into Postgres, so no request pays to query them. Its inner modules build the picture: `astronomy/` (ecliptic, projection, and sidereal time), `drawing/` (stars, lines, colors, SVG, and view), and `options/` (the input and measurements a request carries).

## Event Metrics

`eventMetrics(input: EventMetricsInput!)` measures, in SQL, the events that overlap a `period` and meet a `filter`, as a whole (`total`) and for the tree of groups a `grouping` makes (the same `EventGroupLevelInput` levels the `events` query reads). It lives in `src/modules/events/modules/metrics`: `modules/catalog` (the catalog tables), `modules/measures` (the code registry and the SQL of each aggregate), `modules/facts` (the one statement over the `event` grain), `modules/rollups` (the day grains), `modules/query-building` (the per-level statements on the base tables), `modules/inputs`, `modules/results` and `modules/tree`.

- **The catalog is data, the computation is code.** `measures`, `metrics` and `metric_expressions` (a closure-table tree, loaded with `getTreeRepository(MetricExpression).findTrees()`) are seeded by the caelundas-db migration. A measure row is only `slug`, `name`, `icon`, `note` and `unit`; a metric row is the same plus `expression_id`, the root node of the tree that composes it (a node is a measure, another metric through `metric_id`, or an operator over its children in `position` order; there are no number nodes, the percent is the operator `percent`, `100 * a / nullif(b, 0)`). `EventMetricsCatalogService` loads them once, builds each tree, and fails the load on a measure with no registry entry or another unit, a registry column the real `calendar_event_facts` lacks (checked against `pg_attribute`), a malformed tree, an unknown operator or a metric that reads itself. `eventMetrics` takes metric **slugs**; an unknown one is a bad request that lists the known ones. `eventMetricCatalog` answers `measures { slug name icon note unit }` and `metrics { slug name icon note unit additive measures }` in the picker's order.
- **The measure registry** (`MEASURE_REGISTRY` in `modules/measures/event-metrics-measures.constants.ts`, keyed by measure slug) says how each of the 19 measures is computed: its `aggregate` kind, the facts `column` it reads, an optional `condition` column (`is_progressive`, computed on an event row from its tags), a percentile `argument`, the `grains` that carry it (`event`, and `day` for a measure the facts hold) and its `unit`. Aggregate kinds: `sum`, `count-distinct` (days with events), `distinct-names` (`name` of the events), `distinct-tags` (distinct **direct** tags, counted apart per group), `minimum`, `maximum` (first and last start), `union` (covered time), `span-max`, `span-min`, `span-percentile` (the longest, shortest and median span), `period` (the period's length), `clipped-sum` and `clipped-union` (each event's `start` and `end` clipped to the period; the percent inputs). Eight measures merge across days and read the facts as well; the six that do not and the five that clip (`period-length`, `clipped-duration`, `covered-clipped-duration`, `progressive-clipped-duration`, `progressive-covered-clipped-duration`) read the events only.
- **Derived in code, not stored.** `additive` is true when a metric's expression is one measure that sums, directly or through a metric it reads (events, perfective and progressive events, duration). `zeroIfEmpty` is whatever the expression reads over no events: each aggregate kind has an empty value (a count, sum or union reads 0, a least, greatest or progressive extreme reads none, the period reads a positive number) which `deriveEmptyValue` works through the expression's operators as Postgres does (`x / 0` is none, a none operand makes none), so an average is none and a percent is 0. The picker order is `METRIC_ORDER` (a metric the list lacks follows it by slug).
- **Slugs and units.** Metrics: `events`, `unique-names`, `unique-tags` (distinct direct tags, within `tagRoot`'s subtree when given), `days-with-events`, `perfective-events`, `progressive-events`, `duration`, `covered-duration` (the union of the intervals, so overlaps count once), `average-duration`, `median-duration`, `longest-duration`, `shortest-duration`, `covered-percent`, `total-time-percent`, `progressive-covered-percent`, `progressive-total-percent`, `first-start` and `last-start`. Durations are whole minutes (the facts hold minutes, so a duration needs no conversion), a start is epoch milliseconds and a percent runs from 0 to 100. The average, median, longest and shortest read progressive events only (end after start); perfective events count in `perfective-events` and `events` and add 0 to the sums; `instants`, `spans`, `total-duration` and `progressive-duration` (merged into `duration`, since a perfective event lasts none) still resolve, through `METRIC_ALIASES`; a metric with nothing to read is `null`, and a count or sum is 0.
- **Percent of time**: the four percents divide the minutes of each event's interval clipped to the queried period (the previous period's own length for `previous`) by the period's length; covered is the union of the intervals (0 to 100), total is their sum (it may pass 100); progressive ones only count events carrying Temporality / Progressive; a zero-length period reads `null`. Notes in `documentation/metrics-percent-sql.md`.
- **Statements**: one for the whole set, one per grouping level, and one for the tag names the "No …" groups are called after, run together, or ONE statement over the facts' `event` grain (`modules/facts`: each event once, each level's keys expanded a step a level) when every level is a calendar field or picked tags. A group measures its own distinct events at any depth; an event in two groups of a level counts in both; an event with no key at a level is in the group with a `null` key, labelled `No <name>`, listed last. A level naming a `parent` after a level of the same field splits only the group of that parent tag. Siblings sort by `rank` with digits as numbers and a group returns at most 500 subgroups. No statement is tuned (no `set local`, no JIT or memory settings): the planner is given honest row counts instead. Each level's keys expand through `expand_keys(text[])` and the distinct tags through `expand_tags(uuid[])`, plpgsql set-returning functions of the schema that declare `ROWS 2` and `ROWS 6` (`unnest` of a computed array is assumed ten rows, which multiplied by the levels reached 2.5 million estimated rows against 52 thousand real, so Postgres chose disk sorts, merge joins and JIT), and each level's aggregate and distinct-tag statements are joined on one hashable `gk` text (the period and key path), because a join on the period with the keys as a filter turned into a merge join on the period alone when the estimates ran low.
- **Facts and event rows** (caelundas-db `documentation/metrics-facts.md`): `calendar_event_facts` holds one measure at one filter a row, over every stored event and for the measures that merge across days only; the event path reads each event from `calendar_events` and its tags from `calendar_event_tag_sets` (`FACTS_EVENT_SOURCE_SQL`, a subquery Postgres folds in). An event row has `name`, `start`, `end`, local `day` and `hour`, `duration_minutes`, `tag_ids` (the tags put directly on the event) and `ancestor_tag_ids` (their proper ancestors); every measure column (`events`, `instants`, `spans`, `progressive_minutes`, `first_start`, `last_start`, `covered_range`, `span_duration_minutes`, `is_progressive`) is computed from those (`FACTS_EVENT_COLUMN_SQL`). Overlap with a period is `start < period_end and "end" >= period_start` on the btree `(start, end)`. So a tag filter or tag grouping reads `tag_ids || ancestor_tag_ids` (`FACTS_TAGS_MATCHING_SQL`) while `unique-tags` counts the direct `tag_ids`. `RAW_EVENT_COLUMN_SQL` computes the same columns from the base tables for the per-level fallback statements, and the integration tests assert both paths return identical results.
- **Routing**: the facts (`modules/rollups`) answer a request only when it has no `filter` and every measure it reads merges across days (the registry's `grains` carry `day`: `events`, `perfective-events`, `progressive-events`, `duration`, `first-start`, `last-start`, `days-with-events`); the six that do not (`unique-names`, `unique-tags`, `covered-duration`, `longest-progressive-duration`, `shortest-progressive-duration`, `median-progressive-duration`) and the five percent inputs send the whole request to the events. When the facts apply, a guard statement names the zone they answer in (every event shares one timezone and each period starts and ends at that zone's local midnight), events that start before a period and reach into it are added from the events, and the whole set, a calendar field level (`day`, `month`, `quarter`, `year`) and the first level of a tag's children read them: the day (or day-and-tag) filters whose `period` is in the window are pivoted back to columns, one conditional aggregate a measure. A level they cannot answer falls back to the facts-less event statement. Durations are whole minutes, which is exact for events recorded at minute resolution; instants are epoch milliseconds in the facts.
- **One more level of children, always.** Every group of the tree also carries its child tags, so a chart can stack any bar and a row opens at once. For each tag group that the grouping does not split (the last level's, and, where a level refines one parent tag only, every other group above it), the same statements measure the tags beneath it that its events carry: one more key-expansion step in the facts statement (`FACTS_CHILD_LEVEL_SQL`, `tag_edges` from the last level's tag, only when that level picks tags), one more statement on the rollups (`ROLLUP_CHILD_TARGET`, for one plain tag level) or on the events (`request.children`: `EVENT_METRICS_CHILDREN_SQL` runs the level chain without dropping a skipped level, takes the children of its last row's effective tag from `tag_edges` among the tags the event's `calendar_event_tag_sets` row holds, groups them in a `kids` CTE, and names them once, after grouping, by their path beneath the host) otherwise; the facts name them through the `children_dim` CTE, a hash join, never a lateral per row, which pushed the estimated cost over the JIT thresholds; a grouping of calendar fields has no tag to open and no statement. A tag under two parents appears under each. The rows come back as `MeasuredRows.children`, and `buildMetricTree` hangs them beneath their host as groups with `isPreview: true`, `level` the host's plus one and the id `<host id>/<level>:<key>`; they hold no children (one level only), no "No …" group stands for the events with none of them, and a host's own values are its own, never the children's sum. The web lists no preview among the table's group ids.
- **Local time without a view**: the events list, facets, calendar-field filters, grouping keys and raw metric statements read `EVENTS_LOCAL_SQL` (`event-filter-sql.constants.ts`), `calendar_events` with its stored generated columns `start_local_day`, `end_local_day` and `start_local_hour` (cast to text and integer for the readers) and `duration_minutes` and `temporality` computed inline; the weekday is `extract(dow from start_local_day)`. Tags at query time: a statement that needs a tag's depth, root, path or rank starts with the `tag_paths` and `tag_info` CTEs (`TAG_INFO_SQL`, whose `with recursive` is its first word): `tag_paths` walks `tag_edges` from the roots and has a row for each path a tag sits at (depth, root, parent, path and rank path), so a tag with several parents has several; `tag_info` keeps one row a tag, its shortest path and then the first by rank, for what needs a single path. A tag's depth is its shortest path's, a facet lists the tag once a path with one id (`alsoUnder` names its other parents), an event's `tags` lists it once a path (the web draws one pill), and a group level keeps one row a tag, the path whose depth is the level's. The "No …" groups and the tag trees read are over ids, so an event counts once however many paths lead to a tag.
- **Comparing**: `compareToPrevious` also measures the period of equal length right before, in the same statements, and sets each value's `previous`, matched by group id. A group only the previous period had is returned with empty values (`value` 0 or `null`) and its `previous` set, so a client can show it as gone.
- **Facet menu flags**: `facets` roots and values carry `isFilterable`, `isGroupable`, `isSelectable`, `isSortable` and `isDefaultGroup` (the tag's columns, `true` unless the CLI's `TAG_MENU_EXCLUSIONS` names it; `isDefaultGroup` is false for the attribute roots Body and Temporality, the ones events are not grouped by when no level is picked). They tell the web's menus what to offer, and the API enforces them silently: `TagFlagsService.sanitize` (`modules/tag-flags`) runs at the resolver boundary of `events` and `facets` (`eventMetrics` calls it with its filter and grouping levels as `levels`) and drops, with no error, warning or list of what it dropped, a filter value naming a tag whose `is_filterable` is false (a rule left with none is dropped) and a group or color level naming a tag, or a root, whose `is_groupable` is false (a picks level left with none is dropped). Sort and columns are the web's, which drops them from the link on load.
- **Event and tag fields**: a `CalendarEvent` has `name` and `note` (the database's `name` and `note` columns), no `color` or `location`; tags, facets and facet values carry a `slug`.
